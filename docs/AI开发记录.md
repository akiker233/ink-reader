# AI 开发记录

本篇按考核题交付物第 4 条要求记录：**哪些部分用了 AI、用到什么程度、如何与 AI 交互、结果如何。**

为了不只写「用了 AI」，下面把「AI 做对了什么」和「AI 做错了什么、怎么被发现的」分开写 —— 后者更能说明这套代码是不是真的被理解过。

---

## 一、总体情况

| 项 | 情况 |
| --- | --- |
| AI 工具 | Qoder（具备文件读写与浏览器自动化能力的编码 Agent） |
| 编码占比 | **几乎 100% 的代码由 AI 生成**，由人负责决策、验收与纠错 |
| 人的介入点 | 技术选型、功能范围、UI 观感验收、缺陷复现与拍板 |
| 迭代轮次 | 六轮：① 初版（考核最低功能 + 进阶）② 追加 Markdown 支持 ③ 适配并优化移动端 ④ 追加「Markdown 目录可不按 # 切分」⑤ 支持 Esc 返回（并顺带修掉浮层 Esc 冲突、补上 `==高亮==` 与正文分章认 `#` 的缺口）⑥ 部署上线，并按验收反馈补 `PasteDialog` 的 Esc、给分章模板的选取加权重 |
| 交互次数 | 6 个主提示 + 11 次选项式决策 + 约 27 轮缺陷修复 |
| 未使用 AI 的部分 | 无 |

> 诚实说明：这不是「AI 辅助手写」，而是「人下判断、AI 写全部代码」。
> 所以按考核题说明第 3 条，本文重点写**代码是怎么被校验的**，而不是「AI 有多强」。

## 二、交互过程

### 1. 唯一的初始提示词

```
根据文档完成项目二，做一个网站
```

附带文件：`比特工场2026秋招程序组考核题.md`。

这是全部需求输入。文档里只规定了项目二（文本阅读器）的**最低功能**和**评分维度**，没有规定技术栈、页面结构、交互细节。所以 AI 做的第一件事不是写代码，而是**把模糊需求收敛成可执行范围**。

第二轮追加需求同样只有一句话：「添加对 markdown 的支持」（见第五节）。

第三轮同样只有一句话：「适配并优化移动端」（见第六节）。

第四轮同样只有一句话：「修改：md可以选择不根据#切分章节」（见第七节）。

第五轮同样只有一句话：「支持按 esc 返回」（见第八节）；这一轮的两处浮层 Esc 冲突与两个缺口，都是 AI 在实现时自己暴露、由人点头后一并处理的。

第六轮没有新提示词，是人逐条回复上一轮列出的四个「待拍板」项（见第九节）。

### 2. AI 反问了决策问题（选项式）

AI 没有直接开写，而是用「给出选项 + 推荐项 + 取舍说明」的方式提问，由人拍板。

**第一轮（技术栈与范围）**：

| 问题 | 人选的方案 | 候选 |
| --- | --- | --- |
| 技术栈 | **Vue 3 + Vite + Pinia** | 原生 JS 单文件 / React / Vue 3 |
| 功能深度 | **进阶版**（最低要求 + 编码识别、章节目录、书签、全文检索、快捷键、统计） | 只做最低要求 / 进阶版 |
| 部署方式 | **Cloudflare Pages** | GitHub Pages / 本地运行 |

**第二轮（Markdown 范围）**：解析实现方式 / 语法覆盖程度 / 目录来源 / 格式判定依据，四个问题的选项与理由见第五节第 1 条。

**为什么先问再写**：这些决策会改变几乎每个文件的写法（状态管理方式、持久化策略、构建配置、渲染管线）。一旦写歪，返工量远大于问一句的成本。

### 3. 实施顺序

AI 自行拆成 6 步，并按依赖顺序推进：

1. 工程骨架（`package.json` / `vite.config.js` / `index.html` / `.gitignore`）
2. 工具层（`utils/`：IndexedDB、编码识别、章节识别、主题、持久化）—— 纯函数，最容易独立验证
3. 状态层（`stores/`：`ui` / `settings` / `shelf` / `reader`）
4. 界面层（`components/`：书架页、阅读页、抽屉、卡片）
5. 构建 + 浏览器实测
6. 文档（README、本篇）

**为什么把工具层放在状态层之前**：编码识别、章节识别是全项目最容易出错、也最容易单独验证的部分。先把它们做成不依赖 Vue 的纯函数，就可以脱离界面单独测，出问题也定位得准。

## 三、AI 生成的代码里，被发现并修正的问题

这一节是本篇的核心。以下问题全部是真实发生的，绝大多数由**浏览器实测**发现，少数由人工观察截图发现。

### A. AI 自己产出的低级错误（在自查中发现）

| # | 问题 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `settings.js` 里混进了 `require`、`void i`、`FONT_FAMILIES && 0` 这类不属于该文件的代码 | 多次改写的残留 | 整个文件按「用 `THEMES.map(t => t.id)` 取主题列表」重写 |
| 2 | `reader.js` 里有 `void ui` 和一个没被使用的变量 | 同上，改完没清 | 删掉无用局部变量，`flushSession` 重写为按增量计算的版本 |
| 3 | `ShelfView.vue` 里出现了第二个 `<script>` 块 | `<script setup>` 与普通 `<script>` 混用 | 合并为一个，组件直接 import |
| 4 | 示例书籍的正文用了 ASCII 直引号 `"` | 生成文本时没注意中文标点 | 全部换成 `「」` |

> 这类问题的共同点是：**单测和构建都不会报错**（`void i` 是合法 JS），只能靠读代码发现。这也是「AI 写完必须有人读一遍」的直接理由。

### B. 靠浏览器实测发现的界面缺陷

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 5 | 章节标题在页面上出现了**两遍** | 章节切片的 `start` 指向标题行，正文又从 `start` 开始渲染，标题行被渲染成正文第一段 | 给章节段增加 `head` 字段（正文起点 = 标题行之后），渲染从 `head` 取内容 |
| 6 | 书架页脚浮在页面中间；窗口约 750px 宽时页脚按钮单独换行 | `.shelf` 不是 flex 容器，页脚不会贴底 | 改成 flex 纵向布局，`flex: none` / `flex: 1 0 auto` 分别管住头尾与网格；补 900px 断点让头部竖排 |
| 7 | 抽屉打开时按 `/` 能打开检索，但**再按别的键全都失灵** | 快捷键处理里用 `if (ui.modalCount > 0) return` 一刀切，把所有键都挡了 | 拆成两段：面板/外观类快捷键（`/ C B S E T + -`）始终生效；只有翻章与滚动类受浮层计数限制 |
| 8 | 字号面板里的「减小」按钮显示成一个**旋转 45° 的 ✕** | 用「加号图标旋转 45°」凑减号，实际转出来是叉 | 在 `AppIcon.vue` 里补一个真正的 `minus` 图标，删掉旋转样式 |
| 9 | 截图工具反复超时；改成主题色后卡顿更明显 | 两处叠加：① `filter: brightness(1.000)` —— 没有实际效果时仍会强制浏览器建滤镜图层，长章节正文全量栅格化；② 滤镜挂在了比视口高很多的滚动容器上 | ① `buildSurfaceFilter()` 无效果时返回 `none`；② 把滤镜移到只占一屏的 `.app` 容器上 |
| 10 | 删除一本书后，1.4 秒内书仍在页面上，看起来像「删除无效」 | **不是 bug**：查 localStorage 与 IndexedDB 都确认已删除，延迟来自页面处于后台时 IndexedDB 被浏览器节流 | 无需改代码；记录为环境现象 |
| 11 | 换字号后**视线落点漂移**（进度百分比没变，但视口顶部的段落换了） | 位置模型只有「章内比例」，重排后按比例换算落点必然落到别的段落 | 新增**段落锚点**：换排版前记下「视口顶压在哪一段、压进多少像素」，重排后按锚点还原（见下节的数据） |

### C. 一个「假故障」的排查

调试后期，浏览器截图工具持续超时、定时器与 IndexedDB 明显变慢。排查结论是**环境问题，不是应用缺陷**：

- 该内嵌浏览器窗口处于**不可见**状态，`document.visibilityState` 返回 `hidden`；
- 浏览器对隐藏页面会**暂停 `requestAnimationFrame`**，实测 500ms 内 **0 帧**；
- 而 Vue 的 `<Transition mode="out-in">` 依赖 `rAF` 推进过渡 —— 过渡永远不结束，于是**点击书封切换页面时界面毫无反应**。

这解释了「点了没反应」的假象。验证方式是用 `setTimeout` 顶替 `rAF` 后，页面切换恢复正常。
此事与代码无关，但值得记录：**同一段代码在不同环境下的表现可能完全不同，报错现场不等于缺陷现场。**

## 四、AI 生成代码的校验方式

不依赖「AI 说没问题」，而是靠三层可复现的证据：

### 1. 构建与产物校验

```bash
npm run build
# 初版：✓ 59 modules transformed.
#       dist/assets/index-*.js   147.46 kB │ gzip: 57.60 kB
# 加入 Markdown 后：✓ 60 modules transformed.
#       dist/assets/index-*.css   34.26 kB │ gzip:  6.97 kB
#       dist/assets/index-*.js   162.91 kB │ gzip: 62.97 kB
```

新增一整个 Markdown 解析器（约 920 行）后，JS 产物从 147 kB 涨到 163 kB（gzip +5.4 kB）。
**没验证的部分**：这里没有去实测「换成 `marked` + `DOMPurify` 会是多少 kB」，所以本文不下「自研更省体积」的结论——选自研的理由是安全不变量只有一处实现（见 README 第五节第 9 条），不是体积，体积只是顺带。

### 2. 真机（浏览器）行为校验

- **真实导入路径验证编码识别**：构造一个 GBK 编码的 txt（含 `第一章 中文` / `第二章 中文`），走真实导入流程，确认识别为 `gb18030`、解码内容正确、切出 2 章 14 字。
- **翻页/检索/书签/删除/设置持久化**：逐项在浏览器里点，并核对 localStorage 与 IndexedDB 的实际内容（不是只看界面）。
- **刷新持久化**：读到 20.7% 后刷新，确认「已读 20.7%」「累计阅读 2 分钟」与上次章节均恢复。

### 3. 关键设计点的量化验证

针对「换字号位置是否保持」这一核心设计声明，做了改前/改后的数值对比（同一章、同一段落）：

| 时刻 | 字号 | 章节滚动量 | 进度 | 视口顶部所在段落 | 段内偏移 |
| --- | --- | --- | --- | --- | --- |
| 改前 | 19px | 422px | 75.61% | 第 1 段 | 122px |
| 改后（放大） | 31px | 1569px | 75.61% | **第 1 段** | **122px** |
| 再改（缩小回） | 19px | 422px | 75.61% | **第 1 段** | **122px** |

滚动量变了 3.7 倍，进度与视线落点**完全没动**。

作为对照，**只**用比例还原时（未加锚点前）同样条件下的实测结果是：
段落索引由 `0` 漂到 `1`，进度仍是 30.32% —— 说明「进度数字不变」不等于「位置不丢」，两者是两件事。这正是加锚点的原因。

### 4. AI 无法验证的部分（如实列出）

- **真实鼠标点击路径的部分交互**（例如拖动滑块、悬停才出现的删除按钮）在本次不可见窗口环境下无法稳定驱动，这部分改用 store 层调用同一份代码路径来验证。**组件模板本身的部分渲染细节未经真实点击验证。**
- Safari、Firefox 未实测，仅按特性可用性做了取舍（避免使用实验性 API）。

> 关于移动端：初版交付时这一条写的是「未做真机验证」。第三轮补做了设备模拟验证，但仍**不是真机**（见第六节第 4 条）。

## 五、追加需求：Markdown 支持

初版交付后追加的一个需求：「添加对 markdown 的支持」。这里单独记一段，因为它的缺陷密度明显高于第一轮。

### 1. 先反问的四个决策

同样用选项式提问拿到四个决定，之后 AI 才动手：

| 问题 | 选定 | AI 建议的理由 |
| --- | --- | --- |
| 解析怎么实现 | **自研精简解析器** | 引库必须再配一个 HTML 清洗库才敢开 `v-html`；自研能把「先转义、只出白名单标签」做成唯一实现 |
| 语法做到什么程度 | **核心集 + 增强** | 核心（标题/强调/列表/引用/代码/链接/表格/分隔线）+ 任务列表、代码着色、脚注、定义列表 |
| 目录怎么来 | **用 `#` 标题生成，无标题回退** | Markdown 自带层级，比正则猜标题准；层级用「命中最多的那一层」 |
| 怎么判断格式 | **按扩展名 + 可手动切换** | 存的是原文，切换不用重新导入；按书生效而非全局 |

### 2. 编写过程中被发现并修正的 6 个缺陷

这一轮 AI 一次性写了约 920 行，**全部缺陷都是靠自测脚本和通读发现的**，没有一个来自编译报错——解析器是纯字符串拼接，写错了照样能跑，只是默默渲染错。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 引用块会把后面的一行标题吞进引用里 | 惰性续行（不以 `>` 开头的行也算续行）判断漏掉了「这一行其实是块级起点」 | 续行条件补上 `&& !startsBlock(lines, i)` |
| 2 | 脚注引用渲染成字面量 `[^a]` | 脚注定义通常写在引用它的段落**之后**，而收集与渲染在同一趟循环里，渲染到引用处时 `ctx.notes` 还是空的 | 拆出 `collectFootnotes()` 先全扫一遍，返回要跳过的行号集合，再进块级解析 |
| 3 | 渲染自动链接 / 裸 URL 时栈溢出 | `renderLink` 对「标签等于 URL」的情况又走了一遍行内解析，重新命中 URL 分支，无限递归 | 判 `label === url` 时直接按纯文本输出，不再递归 |
| 4 | Markdown 书里检索高亮全部失效 | 行内解析的纯文本兜底调了 `pw(text.slice(i, stop))`，**漏传 `ctx.query`** | 补上第二个参数 |
| 5 | `parseMarkdownChapters` 里有残留代码 | 循环里混进了 `lines.indexOf(line)` 和一个无意义的 `else if (setext && ...)` | 重写为基于下标 `i` 的循环，配预先算好的 `offsets[]` |
| 6 | 调用了不存在的函数 | 工具函数 `nextContentLine` 只在脑中存在 | 补齐实现 |

第 4 条特别值得记：**它不会报错、不会抛异常、界面也正常**，只是高亮静默消失。如果没有断言脚本专门检查「命中词两侧应该有 `<mark>`」，这个问题会一直留到答辩现场才被发现。

### 3. 还有一批「错误」出在测试断言里，而不是被测代码里

自查时先报 FAIL、复核后发现是断言写错了的四处，也都如实记下：

- 嵌套列表的缩进断言没考虑空格，实际渲染正确；
- 把「有效的 https 图片」也断言成 `.img-ref`——设计上**只有无效/不安全**的图片 URL 才降级，有效 URL 渲染成带 🖼 的文字链接；
- 假设空行会切开两个有序列表，实际按 CommonMark 它们合并成**一个松散列表**（改了测试，并另加 `ol start="5"` 的用例）；
- `stripMarkdown` 的代码块长度断言算错了基准。

**这说明「AI 报 FAIL」不能直接当成「代码有 bug」**，得先看断言本身对不对。

### 4. 验证方式

**（1）解析器：100 条断言的 Node 脚本**

脚本留在仓库里（`scripts/md-selftest.mjs`，`npm run test:md`），零依赖、纯 Node 跑。覆盖块级 / 行内 / 脚注 / 安全 / 边缘 / 章节识别 / `stripMarkdown` / 性能八组：

```
通过 100 / 失败 0
渲染 8000 行耗时 34ms，产物 555999 字符
```

「安全」一组是重点：`<script>`、`<img onerror>`、`javascript:` / `data:` / `vbscript:` / `file:` 伪协议、内联 HTML 透传，全部单独断言。同时用「未闭合围栏」「未闭合强调」「只有表头的表格」「空引用行」「20k 字符单行」做边缘兜底，保证**任何畸形输入都只产出错误的排版，不产出异常或注入**。

**（2）浏览器实测（生产构建 + store 探针）**

用一份含全部语法 + XSS 载荷的样本走真实导入路径，实测结果：

| 检查项 | 结果 |
| --- | --- |
| 章节生成 | `['前言', '第一章 标题探测', '第二章 结束']` —— `##` 命中 2 次被选为章节层，`#` 落进「前言」 |
| XSS 是否执行 | `window.__XSS_SCRIPT__` / `window.__XSS_IMG__` 均为 `undefined`；DOM 里 `script` / `img` 元素数 **0** |
| XSS 呈现 | `&lt;script&gt;…` 以字面量文本显示 |
| 伪协议链接 | `javascript:alert(1)` 的 `<a>` 未生成（`a[href^="javascript"]` 数量 0），降级为纯文本 |
| 正常链接 | `href="https://example.com"`、`target="_blank"`、`rel="noopener noreferrer"` |
| 块级元素数 | `h3`×1、`ul`×3、`ol`×2、`li`×8、嵌套 `ul ul`×1、`blockquote`×1、`pre.code`×1、`table`×1、`hr`×1、`dl/dt/dd` 各 1 |
| 扩展语法 | 任务列表复选框 2 个（1 个 `checked`）、脚注区 1 处、`.fn-ref` 1 处、`.fn-back` 1 处 |
| 行内（前言章） | `h1`×1、`strong`×1、`em`×1、`del`×1、`code`×1 |
| 代码着色 | `.tok--kw`×2、`.tok--cm`×1、`.tok--st`×1、`.tok--nu`×1 |
| 样式生效 | 代码底色 `rgb(239, 231, 215)` = 宣纸主题 `#efe7d7`；关键字色 `rgb(140, 74, 47)` = `#8c4a2f`；`h3` 计算字号 22.04px = 正文 19px × 1.16em |
| 换主题 | 切到暮色后 `--tok-kw` 由 `#8c4a2f` → `#e0857a`、`--code-bg` → `#1d1f24` |
| 格式切换 | 切「纯文本」：章节变为 `['序','1. 有序一','2. 有序二']`、字数 185 → 379、元数据同步；切回 Markdown：章节还原、字数回到 185、**章序号未丢** |
| 检索 | 搜 `粗体` 命中 1 处，结果摘要里的 `#` `**` 标记已被 `stripMarkdown` 擦掉 |

**（3）代码配色的对比度量化**

## 七、追加需求：Markdown 目录可以不按 `#` 切分

### 1. 提示词原文

```
修改：md可以选择不根据#切分章节
```

这一轮没有选项式决策：需求本身只有一句话，剩下的都是「怎么落地」的技术判断（存在哪、切换后进度怎么定位），而这些在第一轮的 `format` 字段上已经有现成答案，照着做即可。

### 2. 落地成一个新字段 `chapterSource`

| 设置 | 取值 | 管什么 |
| --- | --- | --- |
| `format`（既有） | `text` / `markdown` | 正文**怎么渲染** |
| `chapterSource`（新增） | `heading` / `plain` | Markdown 书的目录**从哪来** |

- 复用现成机制：`parseBookChapters(text, format)` 加第三个参数，`'plain'` 直接走原来那套纯文本正则，没有新写解析逻辑；
- 与 `format` 一样按书存进元数据、老数据缺字段就按 `heading`，不用写迁移；
- 与切渲染方式一样按**全文字符下标**重新定位 —— 换口径等于换一套章序号，沿用章内比例会跳到别处；
- 关掉后 `#` 不再被 `head` 偏移吃掉，而是作为正文里的层级标题照常渲染，所以看到的是「一级标题 + 章名分章」的组合，不是标题消失。

### 3. 又一批「错误」出在断言里，而不是被测代码里（第 2 次）

新加的 7 条断言第一次跑就红了 3 条，但三处错的全是**期望值**：

- 纯文本分章在第一个章名之前会插一段「序」（把书名、简介收进去），我照 Markdown 那套「前言」的写法写了期望；
- 同一条断言里取 `chs[0]` 去看正文，而 `chs[0]` 已经是「序」了，切片自然不含第一章的内容。

改断言，代码一行没动。这和第五节第 3 条是同一个模式：**测试脚本本身也是 AI 写的，同样会错**，红了先分清是代码错还是断言错。

### 4. 一次「假故障」：点开关后进度从 74 跳到 82

界面实测时，点完开关偏移由 74 变成 82，看着像是丢了进度。分两步定位：

1. 把动作单独同步跑一遍（不经过视图）：`setChapterSource` 前后偏移稳定在 **50 → 50 → 50**（heading ↔ plain 往返），动作本身没问题；
2. 换一条不经改动的新路径复现：同一本书上 `goChapter(2, 0.5)`，偏移**同样从 72 跳到 82**。

原因在阅读页既有的 `applyScroll`：内容不足一屏（`max ≤ 4px`）且当前正好是最后一章时，比例直接置 1 —— 这是第一轮为「短书也得到得了 100%」做的设计取舍。82 字的测试书恰好落在这个特例里。

结论：既有设计行为，不是本轮引入的缺陷；但也说明**验证用的样本要选对**，一屏放得下的文本量不出真实的位置保持能力。

### 1. 提示词原文

### 2. 「按 Esc 返回」难在「谁来响应」

工具栏的返回按钮 `title="返回书架 (Esc)"`、设置面板的快捷键表里早就写着 Esc —— 代码里却没有这个分支，属于「文档承诺了、实现漏了」。补上它只有三行，真正要处理的是**已经有三层浮层各自在监听 Esc**：

| 场景 | 期望行为 |
| --- | --- |
| 无浮层时按 Esc | 从阅读页返回书架 |
| 目录抽屉开着 | 只关抽屉，不退出阅读 |
| 窄屏「更多」菜单开着 | 只关菜单，不退出阅读 |
| 确认框叠在抽屉上 | 只关确认框，抽屉留着 |

难点出在一个 DOM 事件细节上：抽屉和对话框的监听都挂在 `window` 的**捕获阶段**，用的是 `stopPropagation()`。它挡得住事件「继续往 target / 冒泡阶段走」，却**挡不住同一个节点、同一阶段上的另一个监听器** —— 那要靠 `stopImmediatePropagation()`。所以确认框叠在抽屉上时，一次 Esc 会把两层一起关掉。

修法是**不指望事件传播去仲裁，各层自己判断该不该响应**：

- `AppDrawer`：`if (ui.dialog) return` —— 确认框在上面，这一下 Esc 归它；
- `ReaderToolbar` 的「更多」菜单：自己接一个捕获监听，关掉菜单并 `stopPropagation`，事件就走不到 ReaderView；
- `ReaderView` 的全局快捷键：加 `if (e.key === 'Escape') { reader.closeBook(); return }` —— 能落到这一行的 Esc，一定没有浮层在管它。

### 3. 顺手补的两个缺口

这是上一轮报告里列出的两个「可选改进」，由人点头后一并做掉：

- **`chapterSource='plain'` 时认不出行首的 `##` 章名**。正文里的章名常常带 ATX 标题符（`## 第一章 出发`），而纯文本那套章节正则是行锚定的、看不见行首的 `#`，于是整篇只剩兜底切节。修法：拿去匹配前先 `headingText()` 摘掉标题符。
- **`==高亮==` 被原样渲染**。补一条行内规则，输出 `<mark class="hl">`；类名与检索命中分开，底色从主题 `accent` 现算（`color-mix`），文字沿用正文色。

### 4. 一次自己抓到的设计错误

摘掉标记之后，「标题」不再是原行里的连续子串，于是原来那句 `offset + rawLine.indexOf(title)` 会返回 `-1`；更隐蔽的是：行首带 `## ` 时，章节起点若仍落在标题文字上，「第一章之前算序」就会把那截 `## ` 当成正文，凭空多出一个空的「序」章。

改成**认行首第一个非空白字符**作章节起点，并在自测里加了一条 `start === 0` 的断言专门盯着它。

顺带发现：章节标题在目录 / 工具条 / 页面抬头三处都是当纯文本插值的，源文件里写 `## 四、==验收==` 就会把 `==` 原样挂到目录上（正文里那对 `==` 却已经被渲染成高亮，两边对不上就显得像 bug）。所以标题也过一遍 `plainTitle()` 擦掉行内标记。

## 九、第六轮：部署上线，以及验收反馈的两处收尾

### 1. 提示词原文

部署完成后，人对上一轮列出的四个「待拍板」项逐条回复：

```
1.按你说的来
2.补
3.做
4.cf pages已完成部署
```

即：提交粒度按 AI 的判断办；补 `PasteDialog` 的 Esc；做分章加权；Cloudflare Pages 已在 Dashboard 部署完毕。

### 2. 分章模板的选取：给「带 `#` 的命中」优先权

**问题**：把一份 `.md` 切成「按正文规则分章」时，正文里的 `1.` `2.` 列表项同样命中编号模板，数量上常常压过真正的 `## 一、` 标题 —— 考核题那份文件就被切成 10 个「章」（9 条列表项 + 序），而它其实只有 6 个 `##` 小节。

**做法**：行首带 `#` 的命中（作者明确写成标题的行）单独计数；只要有模板拿到 ≥2 个这种命中，就只在这几条模板里选。纯 txt 没有 `#`，这一步等于不生效，行为与原来完全一致。

**为什么不是「简单加倍」**：最初想的是把带 `#` 的命中原量 2 分。但列表项的数量没有上界 —— 一份文档里几十条 `1.` 对 6 个标题，权重 2 依然会输。改成「有可信标题就只信标题」之后，「数量」这个不稳定的因素被整个移出了判据。

### 3. `PasteDialog` 补 Esc

补法和其他浮层一致：打开时挂 `window` 捕获阶段的 `keydown`，`Esc` → `emit('close')`。这里**没有**加「确认框盖在上面就让路」的判断 —— 粘贴框是全屏遮罩，且书架上没有全局快捷键，确认框不可能叠到它上面；只有可能发生的分层才值得写判断。

## 十、结论

| 维度 | 结论 |
| --- | --- |
| AI 适合做什么 | 一次性铺出大量结构清晰的样板（工具函数、store、组件骨架），速度快、命名一致 |
| AI 不适合独自做什么 | ① 产出物里的**残留代码**（不会报错，只能靠读）；② **视觉观感**判断（对齐、间距、图标语义）；③ **跨文件一致性**（一个字段漏传，标题就渲染两遍）；④ **静默失效的逻辑**（高亮不生效但不报错，见第五节第 2 条） |
| 人的价值在哪 | 给出正确的范围和取舍、实测复现现象、判断「这是缺陷还是环境问题」、判断「这是代码错还是断言错」 |
| 本次最大教训 | ① **「进度没变」和「位置没丢」是两件事**，只有量化测量才会暴露差异；② 报错现场不等于缺陷现场，环境因素要先排除；③ **不报错 ≠ 正确**，纯字符串拼接类的代码必须靠断言兜底；④ 写在媒体查询里**不会**提高 CSS 的优先级 —— 「我写了但没生效」多半是选择器特异性问题，读一遍计算样式就能定位（第六节第 3 条） |

**如果重来一次会改什么**：先把「编码识别」「章节识别」也写成带断言的测试脚本再接入界面 —— 这两个模块的下游影响面最大，第一轮是靠手工构造样本验证的，成本偏高。

这一点在第二轮被验证了：Markdown 解析器**先写了 100 条断言的脚本再接入界面**，6 个缺陷里有 4 个（脚注、递归、检索高亮、章节残留代码）是在脚本里第一次暴露的，没有一个需要去界面上肉眼找。脚本留在 `scripts/md-selftest.mjs`，可复跑。
